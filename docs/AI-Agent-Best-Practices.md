# AI Agent 最佳实践经验文档

> 本文档整理了在 AI 编程助手协作过程中积累的可复用经验，涵盖问题分析方法论、Agent/Skill 设计模式、以及性能优化策略。

---

## 一、问题分析与解决框架

### 1.1 问题解析阶段

当收到一个问题时，按以下优先级解析：

| 步骤 | 名称 | 说明 |
|------|------|------|
| 1 | **意图识别** | 用户真正想要什么？区分表面需求和深层需求 |
| 2 | **范围界定** | 单文件修改？跨模块重构？还是架构设计？ |
| 3 | **约束提取** | 技术栈限制、现有模式、用户偏好 |
| 4 | **歧义检测** | 如果有多种理解方式，立即询问而不是猜测 |

### 1.2 上下文收集策略

- **并行探索**：对不熟悉的代码库，同时启动多个探索任务，覆盖不同目录和角度
- **由粗到细**：先看项目结构（package.json、目录布局），再看具体文件
- **模式识别**：找到代码库中已有的模式/约定，遵循它们而不是发明新的
- **关联追踪**：从 import 关系、类型定义、配置文件入手，分析一个改动会影响哪些文件

### 1.3 有效的提示词模式

#### a) 角色设定（Role Priming）

```
你是一个专注于 [领域] 的高级工程师，擅长 [具体技能]。
```

**作用**：缩小输出空间，减少泛泛而谈。

#### b) 结构化约束（Structured Constraints）

```
要求：
- 使用现有的 XX 组件库
- 遵循项目中的 YY 模式
- 不要引入新依赖
```

**作用**：明确边界，避免过度工程化。

#### c) 示例驱动（Few-Shot）

```
参考现有的 UserService 实现方式，为 DeviceService 创建类似的服务层。
```

**作用**：比抽象描述高效 10 倍。

#### d) 思维链引导（Chain of Thought）

```
先分析当前代码的数据流，然后找出瓶颈，最后给出优化方案。
```

**作用**：强制分步思考，减少跳跃式错误。

#### e) 否定约束（Negative Constraints）

```
不要修改 API 接口。不要添加注释解释代码。不要创建新文件除非必要。
```

**作用**：防止常见的"过度帮助"行为。

### 1.4 人格/角色设定实践

| 场景 | 有效的角色设定 |
|------|---------------|
| 代码审查 | "作为安全审计专家，审查这段代码" |
| 架构设计 | "作为有 10 年经验的系统架构师" |
| Bug 修复 | "作为专注于调试的工程师，系统地排查" |
| 重构 | "作为代码质量专家，保持外部行为不变" |

关键原则：**角色设定不是装饰，而是注意力分配机制**。设定"安全专家"会让模型更关注边界检查、输入验证等方面。

### 1.5 规则系统最佳实践

**规则分类**：

- **项目约定规则**：技术栈、代码风格、目录结构约定
- **代码模式规则**：错误处理模式、日志规范、命名约定
- **禁止规则**：不要动的文件、不要用的库、不要改的接口
- **工作流规则**：PR 格式、commit 消息格式、测试要求
- **行为约束规则**：如"每次大改动自动提交"、"使用中文回复"
- **输出格式规则**：回复语言、代码注释风格

### 1.6 问题解决策略排序

```
1. 能复用现有代码 → 复用
2. 能修改现有代码 → 修改
3. 必须新建 → 遵循现有模式新建
4. 全新领域 → 研究 → 原型 → 迭代
```

### 1.7 核心洞察

**上下文 > 提示词 > 模型能力**

给出正确的上下文（哪些文件相关、什么模式要遵循、什么约束要满足），比花时间写完美的提示词更重要。因此：

- `@文件路径` 引用非常有效
- 在规则中写明项目约定非常有效
- 用技能封装重复流程非常有效

## 二、Agent 与 Skill 设计经验

### 2.1 Agent 核心认知

Agent 不是 "LLM + 工具"。**Agent 的本质是决策循环（Decision Loop）**：

```
感知(Perceive) → 推理(Reason) → 行动(Act) → 观察(Observe) → 调整(Adapt)
```

让 Agent 真正有效的不是模型能力，而是这个循环的质量：

| 环节 | 关键问题 | 决定因素 |
|------|---------|---------|
| 感知 | 给 Agent 什么上下文？ | 决定 80% 的效果 |
| 推理 | 如何分解问题？ | 规划能力 |
| 行动 | 工具设计是否合理？ | 工具粒度 |
| 观察 | 是否检验了执行结果？ | 自验证 |
| 调整 | 遇到错误如何恢复？ | 容错能力 |

### 2.2 三种 Agent 模式

#### 模式 1：Plan-then-Execute（先规划后执行）

```
用户需求 → 收集上下文 → 制定计划 → 用户确认 → 逐步执行 → 验证结果
```

**适用场景**：跨多文件的重构、新功能开发、架构变更。

**核心价值**：避免"写到一半发现方向错了"。在规划阶段发现问题的成本远低于执行阶段。

#### 模式 2：并行探索（Parallel Exploration）

面对不熟悉的代码库时，同时启动多个子 Agent 探索不同方向：

```
主 Agent
  ├── 子 Agent 1: 探索目录结构和技术栈
  ├── 子 Agent 2: 搜索相关代码模式
  └── 子 Agent 3: 分析依赖关系
```

**核心价值**：时间成本从串行的 O(n) 变成并行的 O(1)。

#### 模式 3：专家委派（Expert Delegation）

不同类型的任务委派给不同"专家"：

| 专家类型 | 擅长领域 |
|---------|---------|
| explore | 快速代码搜索和结构理解 |
| shell | 命令执行和环境操作 |
| generalPurpose | 复杂多步推理 |
| browser-use | UI 测试和验证 |

**核心价值**：每个专家有自己独立的上下文窗口，不会互相干扰。

### 2.3 Skill 的本质

Skill 是**可复用的认知程序**，不是文档，不是教程。它把"我知道怎么做 X"编码成可重复执行的程序。

一个好的 Skill 应该包含：

```
1. 触发条件（When）：什么时候应该使用这个 Skill？
2. 前置检查（Check）：执行前需要确认什么？
3. 执行步骤（Steps）：具体怎么做？
4. 决策点（Decisions）：遇到分支怎么选？
5. 验证标准（Verify）：怎么知道做对了？
6. 示例（Examples）：成功案例长什么样？
```

### 2.4 Skill 质量标准

**坏的 Skill**（太抽象，无法直接执行）：

```
"创建一个组件时，要遵循项目约定。"
```

**好的 Skill**（具体可执行，不需要额外判断力）：

```
"创建 React 组件时：
1. 在 src/components/ 下创建目录，使用 PascalCase 命名
2. 从 src/components/Button/index.tsx 复制结构模板
3. Props 类型定义放在同文件顶部，命名为 {ComponentName}Props
4. 使用项目中的 cn() 工具函数处理 className 合并
5. 导出时在 src/components/index.ts 添加 re-export"
```

### 2.5 Skill 设计的分层模型

```
Level 1 - 知识层（Knowledge）
  "我们项目用 Tailwind CSS"
  → 适合放在 Rules 里，不需要 Skill

Level 2 - 流程层（Procedure）
  "创建新页面的完整步骤"
  → 适合做成 Skill，步骤明确可重复

Level 3 - 策略层（Strategy）
  "根据需求选择合适的状态管理方案"
  → 适合做成高级 Skill，包含决策树

Level 4 - 元层（Meta）
  "如何创建新的 Skill"
  → 用于指导 Skill 本身的创建
```

分层原则：**只有 Level 2 及以上才值得做成 Skill，Level 1 放 Rules 更合适**。

### 2.6 六条实战经验

#### 经验 1：上下文工程 > 提示词工程

90% 的 Agent 效果提升来自给正确的上下文，而不是写更好的提示词。

- 自动注入项目规则：让每次对话都自动带上项目约定
- 文件引用优于描述：`@src/components/Button.tsx` 比用文字描述组件结构高效 10 倍
- 示例代码优于抽象要求："像 XXX 文件那样做" 比 "写一个优雅的实现" 有效 100 倍

#### 经验 2：工具粒度决定 Agent 能力上限

- **粒度太粗**：一个工具做太多事 → Agent 无法精细控制
- **粒度太细**：太多小工具 → Agent 决策负担过重，容易选错

最佳粒度原则：**一个工具 = 一个原子操作 + 明确的输入输出**。

```
ReadFile(path) → content            # 原子操作：读一个文件
SearchCode(pattern, scope) → matches # 原子操作：搜索匹配
EditFile(path, old, new) → result   # 原子操作：替换内容
```

#### 经验 3：错误恢复是区分玩具和产品的关键

大多数 Agent 教程只讲 happy path。实际上 Agent 50% 的时间在处理意外：

```
文件不存在 → 搜索正确路径
编辑冲突 → 扩大上下文重试
命令失败 → 分析错误信息，调整参数
结果不对 → 回退并尝试替代方案
```

可复用模式：**每个工具调用后都应该有"结果检验 → 异常处理"的分支**。

#### 经验 4：记忆系统的三层架构

```
即时记忆（Working Memory）
  = 当前对话上下文
  → 处理当前任务的信息

会话记忆（Session Memory）
  = Todo List、Plan
  → 跨多个步骤保持一致性

持久记忆（Long-term Memory）
  = Rules、Skills、项目配置
  → 跨所有对话保持项目约定
```

关键洞察：大多数人只关注即时记忆（写更好的 prompt），忽略了持久记忆（Rules 和 Skills）的巨大价值。花 30 分钟写好的一条 Rule，会在之后的每次对话中自动生效。

#### 经验 5：人机协作的最优分工

```
人类擅长：意图表达、质量判断、创意决策、边界情况识别
Agent 擅长：信息检索、模式匹配、重复执行、一致性保持
```

最高效的模式不是让 Agent 完全自主，而是：

- **人类**：定义"做什么"和"约束条件"
- **Agent**：负责"怎么做"和"执行验证"
- **人类**：审核结果和方向修正

#### 经验 6：Skill 的生命周期管理

```
发现重复操作 → 手动执行 2-3 次 → 提炼成 Skill → 使用并优化 → 稳定后固化
```

不要一开始就试图写"完美的 Skill"。**先做，再总结，再抽象**。

## 三、快速响应机制

### 3.1 并行化（最大的加速器）

#### 工具调用并行化

```
❌ 慢的方式（串行）：
读文件A → 等结果 → 读文件B → 等结果 → 搜索代码 → 等结果
总耗时 = T(A) + T(B) + T(搜索) ≈ 3秒

✅ 快的方式（并行）：
同时发起：读文件A + 读文件B + 搜索代码
总耗时 = max(T(A), T(B), T(搜索)) ≈ 1秒
```

关键规则：**如果多个操作之间没有依赖关系，就在同一条消息中同时发起所有调用**。

#### 子 Agent 并行化

```
主 Agent 同时启动：
  ├── 子 Agent 1: 搜索组件目录 → 0.8秒
  ├── 子 Agent 2: 搜索服务目录 → 1.2秒
  └── 子 Agent 3: 搜索配置文件 → 0.5秒
总耗时 ≈ 1.2秒（取最慢的那个）
而不是 0.8 + 1.2 + 0.5 = 2.5秒
```

### 3.2 模型分级调度

不是每个任务都需要最强的模型：

```
简单搜索/文件查找 → 轻量模型（成本低，速度极快）
复杂推理/架构分析 → 高能力模型（更强推理）
```

原则：**任务复杂度匹配模型能力**。轻量模型处理"在目录里找到所有 `.tsx` 文件"这种任务又快又准，没必要用重量级模型。

### 3.3 专用工具 vs 通用 Shell

```
❌ 慢：Shell("grep -r 'pattern' ./src")
  → 需要启动 shell 进程 → 解析命令 → 执行 → 返回文本

✅ 快：Grep(pattern, path="./src")
  → 直接调用优化过的 ripgrep → 原生集成 → 结构化结果
```

```
❌ 慢：Shell("cat src/index.ts")
  → shell 进程开销

✅ 快：Read("src/index.ts")
  → 直接文件系统调用，零开销
```

专用工具比 Shell 命令快的原因：**省去了进程创建、shell 解析、文本编码/解码的开销**，并且返回结构化数据而不是纯文本。

### 3.4 投机执行（Speculative Execution）

在确认需要之前，提前读取可能需要的文件：

```
场景：用户说"修改 Button 组件的样式"

投机执行策略：
  同时读取：
  - Button/index.tsx      （主文件，大概率需要）
  - Button/styles.css     （样式文件，大概率需要）
  - Button/types.ts       （类型文件，可能需要）
  - tailwind.config.ts    （可能需要看主题配置）
```

即使最终只用到了 2 个文件，但一次性并行读取 4 个文件的成本几乎和读 1 个一样。比"读一个 → 发现不够 → 再读一个"快得多。

### 3.5 上下文聚焦（Context Focusing）

子 Agent 快的核心原因：**它们的上下文窗口非常干净**。

```
主 Agent 的上下文：用户历史对话 + 项目状态 + 规则 + 工具描述...（可能很大）
子 Agent 的上下文：只有任务描述 + 必要工具（极小）
```

上下文越小，模型推理越快。把具体的搜索/探索任务委派给子 Agent，而不是在一个巨大的上下文中执行。

### 3.6 流式输出（Streaming）

```
传统方式：等整个回复生成完毕 → 一次性发送（用户等 5-8 秒才看到内容）
流式方式：每生成一个 token 就立即发送（用户 0.1 秒后就开始看到文字）
```

对用户感知的影响极大，虽然总生成时间不变，但等待感大幅降低。

### 3.7 一次做对（First-Time-Right）

最大的时间浪费是做错了再返工。避免返工的策略：

| 策略 | 说明 |
|------|------|
| 编辑前必须先读 | 避免基于过时/错误认知做修改 |
| 多模式对冲搜索 | 精确匹配 + 语义搜索，减少"找不到 → 换关键词"的循环 |
| 编辑后检查 lint | 立即发现语法错误，避免后续连锁问题 |
| 提前识别歧义就问 | 避免做完一大堆发现方向不对 |

### 3.8 六条性能优化原则

```
原则 1：能并行就不串行（最高优先级）
原则 2：用最轻的工具完成任务（模型/工具匹配）
原则 3：投机性预读取（宁可多读不用，不要少读返工）
原则 4：子任务隔离上下文（每个子 Agent 只看到自己需要的）
原则 5：流式反馈（让用户尽早看到进展）
原则 6：一次做对（前置验证 > 后置修复）
```

## 四、上下文理解与压缩策略

### 4.1 多层上下文解析

每次收到用户消息时，实际处理的不只是用户的文字，而是多层上下文的叠加：

```
┌─────────────────────────────────────────────┐
│ Layer 4: 持久上下文（Rules、Skills、项目配置）  │  ← 跨所有对话生效
├─────────────────────────────────────────────┤
│ Layer 3: 会话上下文（对话历史、Plan、Todo）     │  ← 当前会话内累积
├─────────────────────────────────────────────┤
│ Layer 2: 环境上下文（打开的文件、终端状态、     │  ← 系统自动注入
│          git status、最近浏览的文件）           │
├─────────────────────────────────────────────┤
│ Layer 1: 用户显式消息（当前这句话）             │  ← 用户直接输入
└─────────────────────────────────────────────┘
```

理解需求的过程本质上是**四层信号的交叉验证**，而不是只看用户说了什么。

### 4.2 上下文信号的优先级排序

并非所有上下文信号权重相同。实际的优先级排序：

| 信号 | 权重 | 原因 |
|------|------|------|
| 用户当前聚焦的文件 | 极高 | 用户正在看的就是最可能相关的 |
| 用户显式的 @引用 | 极高 | 明确指向，零歧义 |
| 用户的直接描述 | 高 | 一手意图表达 |
| 终端的活跃命令/报错 | 高 | 如果有报错，大概率是来求助的 |
| git status 中的修改文件 | 中 | 反映用户近期的工作范围 |
| 最近浏览过的文件 | 中 | 可能相关，但也可能只是路过 |
| 已打开但未聚焦的文件 | 低 | 弱信号，仅作参考 |
| 持久 Rules | 始终 | 每次都生效，是行为基线 |

**关键策略：从高权重信号开始验证假设，低权重信号用于补充和消歧。**

### 4.3 从行为推断意图

用户没说的话，往往比说了的更重要。通过行为上下文推断真实意图：

```
场景 1：用户打开了一个文件，光标停在第 42 行，问"这里有问题"
  → 不需要搜索，直接读第 42 行附近的代码

场景 2：终端显示 npm run dev 报错，用户说"帮我看看"
  → 先读终端输出，定位具体错误，而不是问"看什么？"

场景 3：git status 显示 5 个文件被修改，用户说"提交一下"
  → 读 diff 理解改动内容，生成有意义的 commit message

场景 4：用户刚浏览了 A.ts 和 B.ts，问"这两个有什么关系"
  → 直接读这两个文件并分析它们的依赖/调用关系
```

核心原则：**能从上下文推断的就不要问，减少来回交互是效率的关键**。但当推断置信度低时（多种可能的理解），必须主动询问。

### 4.4 面对不同用户的适应策略

不同用户的沟通风格差异会导致不同的理解策略：

| 用户类型 | 特征 | 适应策略 |
|---------|------|---------|
| 精确型 | 给出文件路径、行号、具体需求 | 直接执行，减少确认 |
| 模糊型 | "帮我优化一下"、"感觉不太对" | 先探索代码库，多问一个关键问题 |
| 专家型 | 使用技术术语，知道自己要什么 | 给出技术性回复，不解释基础概念 |
| 探索型 | "有没有更好的方案"、"你觉得呢" | 提供对比分析，给出推荐和理由 |

**是否有偏差？** 客观来说，上下文配置越完善的用户（Rules 写得好、引用精确），得到的结果越准确。这不是"偏差"，而是**信息量决定输出质量**。一个配置了完善 Rules + Skills 的项目，等于给了 Agent 一个"项目专家"的记忆，效果远好于裸聊。

### 4.5 上下文压缩：如何不说废话

这是让输出信息密度最大化的核心机制。

#### 输出压缩的五条原则

**原则 1：信息密度优先于篇幅**

```
❌ 冗长：
"接下来，我将为你修改这个文件。首先，让我来看看文件的内容。
然后我会找到需要修改的部分。最后我会进行修改。"

✅ 紧凑：
直接读文件 → 直接修改 → 说明改了什么
```

不需要"播报"自己的行动计划，直接做。

**原则 2：主动过滤噪声信息**

以下内容会被主动抑制，不出现在回复中：

```
- "我理解你的问题" — 直接回答就是最好的理解证明
- 重复用户的问题 — 用户刚说过，不需要复述
- "这只是一种方案" — 除非确实有重要的替代方案需要讨论
- 对显而易见事情的解释 — 如果代码自解释，不加注释
- 过程性自述 — "让我搜索一下"、"我找到了"
```

**原则 3：用结构替代叙述**

```
❌ 叙述式：
"这个函数有三个参数。第一个参数是 path，它是一个字符串类型，
用来指定文件路径。第二个参数是 options，它是一个对象..."

✅ 结构式（表格/代码块）：
| 参数 | 类型 | 说明 |
|------|------|------|
| path | string | 文件路径 |
| options | object | 配置选项 |
| callback | function | 完成回调 |
```

表格、代码块、列表的信息密度远高于段落文字。

**原则 4：回复长度匹配问题复杂度**

```
简单问题 → 一两句话
  "这个变量在哪定义的？" → "在 src/config.ts 第 23 行。"

中等问题 → 结构化要点
  "这个模块怎么工作的？" → 列出核心流程 + 关键文件

复杂问题 → 分层展开
  "重构这个系统" → Plan Mode → 分步实施
```

**原则 5：行动代替描述**

```
❌ "我建议你可以在第 15 行添加一个 null check，像这样：
if (value !== null) { ... }，这样可以避免空指针异常。"

✅ 直接编辑文件，在第 15 行加上 null check，然后说："已添加空值检查。"
```

能直接做的事不用描述方案。做完说结果比做前说计划更高效。

#### 上下文窗口管理策略

上下文窗口是有限资源。管理策略：

```
输入侧压缩：
  - 只读需要的文件部分（指定 offset + limit），而不是整个大文件
  - 搜索时用精确 pattern，减少返回结果量
  - 子 Agent 只传递任务相关的上下文，不传整个对话

输出侧压缩：
  - 代码变更只展示关键 diff，不复述完整文件
  - 多步操作用 Todo 跟踪，不在每步重复背景
  - 用引用（文件路径 + 行号）替代内联大段代码

对话侧压缩：
  - 每轮对话聚焦一个主题，避免上下文膨胀
  - 复杂任务拆成独立子 Agent，各自维护小上下文
  - 用 Plan 文件持久化决策，不在对话中反复讨论
```

### 4.6 理解上下文的可复用方法论

总结为一个可执行的决策流程：

```
收到用户消息
  │
  ├── 1. 扫描环境上下文（打开的文件、终端、git status）
  │     → 建立"用户当前工作场景"的心理模型
  │
  ├── 2. 解析显式消息
  │     → 提取：目标（做什么）+ 约束（怎么做）+ 范围（影响多大）
  │
  ├── 3. 交叉验证
  │     → 显式消息与环境上下文是否一致？
  │     → 一致 → 高置信度，直接行动
  │     → 矛盾 → 可能有未说明的背景，需要澄清
  │
  ├── 4. 补全缺失信息
  │     → 用持久上下文（Rules/Skills）填充项目约定
  │     → 用代码搜索填充技术细节
  │     → 仍然缺失的关键信息 → 向用户提问（最多 1-2 个关键问题）
  │
  └── 5. 执行并验证
        → 每步执行后检查结果是否符合推断的意图
        → 不符合 → 调整理解，必要时回退
```

关键洞察：**理解上下文不是一次性动作，而是在整个执行过程中持续修正的循环**。初始理解可能只有 70% 准确，但通过执行中的反馈不断收敛到 95%+。

## 五、高效协作技巧（面向用户）

### 5.1 让 Agent 更快更准的沟通方式

- **给 Figma 链接 + 简要说明**：比纯文字描述 UI 需求高效得多
- **指出参考文件**：`"参照 server/agent/tools/xxx.ts 的模式"` 比描述需求更精确
- **分层提需求**：先说大目标，再说具体约束，最后说特殊情况
- **提供错误信息**：直接贴报错比描述"不工作"有用 100 倍

### 5.2 Rule 和 Skill 的投资回报

| 投入 | 回报 |
|------|------|
| 写一条 Rule（5 分钟） | 每次对话自动生效，累计节省数小时 |
| 写一个 Skill（30 分钟） | 重复流程一键执行，质量一致性保证 |
| 提供示例文件引用（10 秒） | 输出质量提升 10 倍 |

### 5.3 何时用 Plan Mode

- 跨多文件的重构
- 新功能涉及架构决策
- 需求不够明确需要讨论
- 修改范围较大需要预估影响

### 5.4 何时直接执行

- 单文件的明确修改
- Bug 修复（有明确的错误信息）
- 添加/修改已有模式的代码
- 简单的配置更改

## 六、五层智能架构（RDK Studio 实践）

### 6.1 架构概述

不将所有智能都塞进 system prompt（会膨胀并降低注意力），而是分层分发：

| 层级 | 载体 | 职责 | 体积控制 |
|------|------|------|----------|
| L1: 身份层 | SOUL.md | 人格、北星原则、输出契约 | <100 行 |
| L2: 工具层 | TOOLS.md + rdk-tools.ts description | 工具环境、组合模式、使用指导 | 工具自带描述 |
| L3: 技能层 | skills/*/SKILL.md | 可复用流程、策略、元技能 | 按需加载 |
| L4: 代码层 | pruning.ts, compaction.ts, DeviceHealthMonitor | 上下文管理、自愈、状态感知 | 零 prompt 开销 |
| L5: 主动层 | HeartbeatManager + HEARTBEAT.md | 定期巡检、异常检测、自动恢复 | 仅心跳触发时加载 |

### 6.2 关键设计决策

**SOUL.md 保持精简**
- 只放身份、原则、行为规则 — 这些是"不变的人格"
- 新增的认知能力（问题分析、错误恢复、并行操作）放入 meta-skills
- 避免"prompt 膨胀"：SOUL.md 每一行都消耗模型注意力

**工具描述即文档**
- 在 `rdk-tools.ts` 的 `description` 字段中包含使用指导和验证方法
- 相关工具间互相引用（如 `doctor → restart → health`）
- 模型每次调用都能看到，不需要额外 prompt

**技能分层加载**
- Level 1（纯知识参考）设为 `disableModelInvocation: true`，不注入 prompt
- Level 2+（流程/策略）动态注入 prompt，通过 SkillManager 统一管理
- 新技能统一使用 `skills/<name>/SKILL.md` 格式

**代码级智能无 prompt 开销**
- 上下文修剪（三层递进：soft trim → hard clear → message drop）
- 主动 compaction（70% 上下文占用时触发，不等消息被丢弃）
- System prompt token 数纳入 pruning 预算（防止隐性溢出）
