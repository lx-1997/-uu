# RDK Studio / RDKCLAW 风险与路线图（管理层版）

## 1. 执行摘要

当前 RDK Studio 已具备“可用产品雏形 + 可落地设备链路 + AI 编排能力”，下一阶段的关键不是“再加多少功能”，而是“把能力稳定地规模化交付”。

建议战略重点：
- 先补质量门禁与可观测性，降低交付风险。
- 再做架构解耦与策略优化，提升研发效率。
- 最后推进生态与多设备协同，扩大平台势能。

## 2. 风险分级总览

| 风险项 | 等级 | 影响范围 | 触发条件 | 建议优先级 |
|---|---|---|---|---|
| 自动化测试与 CI 缺口 | 高 | 所有核心链路 | 发布前回归不足 | P0 |
| 服务端入口耦合偏高（`server/index.ts`） | 高 | API 迭代、故障定位 | 功能持续叠加 | P0 |
| 板端委派依赖链长（SSH+网关+token） | 高 | RDKCLAW 委派体验 | 网络/配置/权限异常 | P0 |
| 双聊天路径并存（`/api/agent/chat` 与 `/api/chat`） | 中 | 认知一致性、维护成本 | 功能继续分叉 | P1 |
| 语音能力在线依赖 | 中 | 合规与离线场景 | 网络受限/隐私要求 | P1 |
| 状态层规模增长风险（前端 Context 门面变胖） | 低 | 可维护性 | 模块继续扩张 | P2 |

## 3. 风险详细说明与动作建议

## 3.1 高风险项（P0）

### A. 自动化测试与 CI 缺口

问题：
- 主工程缺少清晰的测试基线，回归偏依赖手工验证。

后果：
- 功能叠加后故障发现滞后，交付节奏不稳定。

建议动作：
- 增加最小可用测试矩阵（API 烟测 + RDKCLAW SSE 关键事件 + OpenClaw 核心路由）。
- 建立 CI 基线（类型检查、构建、最小测试集）。

衡量指标（建议）：
- 关键 API 覆盖率 >= 70%（先覆盖高价值链路）。
- 回归缺陷率季度环比下降 30%。

### B. 服务端耦合偏高

问题：
- `server/index.ts` 集中大量路由与运行时逻辑，变更风险累积。

后果：
- 新功能冲突概率升高，问题定位时间拉长。

建议动作：
- 按域拆分：`agent-routes`、`openclaw-routes`、`rdkclaw-routes`、`ecosystem-routes`。
- 引入统一错误模型与日志上下文（runId/sessionId/deviceId）。

衡量指标：
- 单文件体量与变更热区持续下降。
- 平均故障定位时间（MTTR）下降 25%。

### C. 板端委派链路稳定性

问题：
- 委派成功依赖多个条件同时成立（连接、网关、token、插件等）。

后果：
- 用户主观体验“偶发失效”，影响对智能体可信度。

建议动作：
- 增加预检门禁：执行前自动健康探测并给出可执行性说明。
- 失败回退策略固化：委派失败自动切本地工具并提示。
- 可观测性增强：把失败归因标准化展示在 UI。

衡量指标：
- 委派任务成功率 > 90%（分场景统计）。
- 委派失败后二次恢复成功率 > 80%。

## 3.2 中风险项（P1）

### A. 双聊天路径并存

问题：
- 同时存在传统 `/api/chat` 与新主链 `/api/agent/chat`。

建议动作：
- 给旧路径明确退役计划：限定用途、下线时间、替代说明。
- 统一前端默认入口到 `/api/agent/chat`。

衡量指标：
- 新链路流量占比 >= 95%。
- 旧链路仅用于兼容模式并有审计记录。

### B. 语音在线依赖

问题：
- STT/TTS 部分依赖在线能力，存在合规与离线限制。

建议动作：
- 规划离线 STT/TTS 插件能力包作为可选部署。
- 在策略面板明确“在线/离线”能力差异与风险提示。

衡量指标：
- 离线模式覆盖核心场景比例逐季提升。

## 3.3 低风险项（P2）

### 前端状态扩展性

建议动作：
- 逐步把超大 Store 逻辑拆分为领域 hooks 与 selector。
- 对事件解析模块做薄层抽象，减少 UI 组件逻辑负担。

## 4. 路线图（短中长期）

## 4.1 短期（1-3 个月）：稳态与可信

目标：
- 稳定主链路，建立最小质量与观测护栏。

技术动作：
- 建立 CI（typecheck/build/smoke test）。
- 对 RDKCLAW 委派链路做健康预检与降级策略。
- 为关键接口补充契约测试（OpenClaw 路由、审批接口、SSE 事件格式）。

业务结果：
- Demo 到真实场景的转化成功率显著提升。
- 一线反馈中“偶发失败不可解释”问题明显下降。

## 4.2 中期（3-9 个月）：效率与规模

目标：
- 提升研发效率与跨团队协作效率。

技术动作：
- 路由与服务分层解耦，形成明确领域边界。
- 收敛双聊天链路，统一指标体系。
- 打通生态技能 discoverability（让委派策略理解板端已安装技能能力）。

业务结果：
- 需求交付周期缩短，跨团队对齐成本降低。
- 平台能力可复制到更多机器人项目。

## 4.3 长期（9 个月+）：平台化与生态化

目标：
- 从“工具产品”升级为“机器人 AI 能力平台”。

技术动作：
- 多设备/多会话协同（含企业组织权限与审计）。
- 离线与私有化能力包（STT/TTS、策略模板、技能仓库镜像）。
- OpenClaw 版本治理与兼容矩阵自动化。

业务结果：
- 形成标准化行业方案，支持更大规模交付。

## 5. 资源投入建议（用于立项/排期）

- 必需投入（P0）：测试工程 + 服务端重构 + 运维观测（优先级最高）。
- 成长投入（P1）：语音离线化探索 + 路由收敛 + 生态策略打通。
- 战略投入（P2）：平台化能力（多租户、审计、生态治理）。

## 6. 建议的汇报收口话术

- “当前我们已经证明了方向正确与能力可用，下一步重点是把可用变成可复制、可规模化交付。”
- “风险并不在功能不足，而在工程化护栏与系统边界治理，投入产出比最高的动作已经明确。”
- “路线图可分三段推进，每段都有清晰技术动作和业务指标，不是抽象愿景。”
